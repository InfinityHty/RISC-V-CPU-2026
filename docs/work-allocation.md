## 一、项目要完成的工作

最终交付物：**一个乱序执行（OoO）的 RV32IM CPU**（顶层模块 `student_top`，AXI4-Lite 主接口）+ 一份设计报告。评分 = 正确性（85） + 性能（15） + 频率加分（4）。

工作可拆成 6 大块：

**1. 环境搭建（约半天，谁先谁做）**
- 拿到 AppImage（或先用 Docker 方案 `docker build -t cpu2026 .` 顶替，二者 `make` 命令完全等价）
- 验证 `make build / make test / make synth` 能跑通

**2. 架构设计（第 1~2 周，两人一起）**
- 确定微架构：Tomasulo + ROB 是标准选择
- 定参数：发射宽度、ROB 深度、RS 深度、PRF 大小、Cache 配置
- 画出模块划分图和内部接口定义（这是分工的前提）

**3. 顺序执行基线 CPU（强烈建议先做）**
- 先写一个单发射顺序执行（甚至多周期）的 RV32IM CPU，跑通基本测试
- 价值：拿到 75 分保底（向量乘、向量加、0~100 求和三个基础测试），同时把 AXI4-Lite 接口、取指、译码、访存这些"脏活"先做对，后续 OoO 改造是在能工作的代码上迭代

**4. OoO 核心模块（主体工作量）**
- 前端：取指（I-Cache）、分支预测（BTB/BHT）、译码
- 重命名与发射：寄存器重命名（RAT）、ROB 分配、保留站（RS）、发射逻辑
- 执行：ALU、乘除法器（M 扩展）、Load/Store Unit、旁路/转发
- 提交：ROB 退休、精确异常（分支误预测恢复）、RAT 提交
- 存储：D-Cache（用框架的 `sram_fakeram`）、AXI4-Lite 访存调度
- 结束约定：向 MMIO 地址 `0x80000000` 写返回码

**5. 验证、综合与调优**
- 跑全部 `correctness_*`（20 个）→ 85 分
- `make perf` 测 IPC（6 个 `perf_*` 的 GEOMEAN），对照 Tier 表调参数
- `make synth`（先 `MODE=diagnose` 找面积瓶颈，再 `opt` 模式）优化面积和频率（≥300 MHz，冲 400/500 MHz 加分）

**6. 报告（最后 1~2 周）**
- 参数敏感性分析（扫 issue width / ROB / PRF / Cache 配置对 IPC 的影响）
- 架构探索中的权衡

时间锚点：第 7 周期中检查，第 14 周周六 23:59 截止。

## 二、两人分工建议

推荐按**前端/后端**纵向切分，接口最干净：

**A 同学（前端 + 提交端，"有序世界"）**
- 取指、I-Cache、分支预测
- 译码、寄存器重命名（RAT）
- ROB、按序提交、误预测恢复
- 后期负责：报告撰写主力、参数扫描实验

**B 同学（执行 + 访存，"乱序世界"）**
- 保留站、发射逻辑、旁路网络
- ALU、MUL/DIV 单元
- LSU、D-Cache、AXI4-Lite 访存
- 后期负责：综合优化（`make synth` 面积/频率调优）

分工的理由：A 的模块全部按程序序工作，B 的模块全部按数据就绪工作，两者的交汇面只有三个——**发射入口、完成回写（CDB）、提交/冲刷信号**，接口数量最少。

另外两个原则：
- **基线 CPU 两人一起写**（或 A 主写 B review），这决定了你们对 ISA 和 AXI 协议的共同理解
- **每周强制集成一次**，不许出现"我的模块单测过了但两个月没合过"

## 三、如何保证接口一致

**1. 先冻结框架级接口**
`student_top` 的 AXI4-Lite 端口是框架定死的（README 里有完整声明），直接抄下来作为 `student_top.sv` 骨架，两人都不许动。

**2. 写一份内部接口契约文档（半天工作量，收益最大）**
开工前在仓库里建一个 `docs/internal-interfaces.md`，为每个模块间接口写清：
- 信号名、位宽、方向
- 握手协议：**统一用 valid/ready**，约定"valid 不依赖 ready 的当周期组合逻辑"（防止组合环）
- 时序语义：数据在 valid && ready 的时钟沿生效

**3. 共享一个参数/定义文件**
建 `verilog/config.svh`（或 package），集中放所有宏和参数：

```systemverilog
parameter ROB_DEPTH   = 64;
parameter RS_DEPTH    = 32;
parameter ISSUE_WIDTH = 2;
// 物理寄存器编号位宽、操作码编码等也放这里
```

两人**只准引用，各自模块里禁止硬编码魔法数**。后期调参也只改这一个文件。

**4. 命名规范**
约定如 `模块A_模块B_signal_valid/ready`、输入 `_i` 输出 `_o`，避免对接时才发现命名冲突。

**5. 接口先行 + 桩模块**
分工定下来后，每人先提交自己模块的**空壳**（只有端口声明 + 简单行为桩），当天就 `make build` 保证顶层能编译连起来。之后各自填实现，接口变了必须先改契约文档、通知对方、再改代码。

**6. Git 协作纪律**
- `main` 分支始终保持 `make test` 全绿，各自功能在 feature 分支开发
- 合并前必须本地跑过 `make test`
- 接口相关的 PR 必须对方 review

**7. 调试手段对齐**
统一用 `make run ... LOG=run.log` 加 `$display` 日志调试（README 也建议别用波形），两人约定日志格式，比如 `[周期] [模块] 事件`，方便互相看对方的日志。
